# ADR 0010: Separate local package integrity from official build origin

- Status: Accepted
- Date: 2026-08-23
- Release: 0.2.0

## Context

The release pipeline can now produce and verify a public, reviewed, rebuild-checked bundle. A running Provelume Instance also needs a local `Verify installation` capability that explains whether installed Core package files have changed.

Python wheel installations normally include PEP 376 `RECORD` metadata. For package and distribution files, `RECORD` can provide a filename, size and URL-safe base64 SHA-256 digest. Comparing installed bytes with those identities is useful for detecting accidental corruption, local modifications, missing files and unexpected additions.

However, `RECORD` belongs to the installed distribution itself. An unofficial or malicious wheel can carry a perfectly self-consistent `RECORD`. A local match therefore proves package-byte integrity relative to that installed wheel, not that the wheel came from an official Provelume release.

Editable development installs are a separate case: package files live in a mutable working tree and may not be represented by immutable wheel payload identities. Showing a green package-integrity state there would be misleading.

## Decision

Provelume will expose three local installation states:

### `package_integrity_verified`

All relevant hashed files declared by wheel `RECORD` match their installed size and SHA-256, no unsafe paths/symlinks are involved and no unexpected regular files are present inside the installed `provelume/` package directory.

This state means only:

> Installed Provelume package bytes match the distribution metadata that installed them.

### `modified_installation`

At least one hard integrity problem is detected, including:

- missing declared file;
- size or SHA-256 mismatch;
- unreadable declared file;
- unsafe/traversal/link-like package path, including filesystem reparse points;
- unexpected regular package file;
- package scan or hashing safety limit reached.

The UI reports the affected paths and does not automatically describe every modification as malicious.

### `verification_unavailable`

A complete result cannot be established, for example because:

- Provelume is not installed as a distribution;
- the installation is editable;
- wheel `RECORD` is absent;
- no relevant package files have SHA-256 identities;
- relevant metadata uses unsupported, missing or malformed hashes;
- the installation root cannot be inspected safely.

This state is not a warning disguised as success.

## Scope and safety

The verifier:

- uses the Python standard library only;
- performs no network requests;
- binds the selected installed distribution to the package tree supplying the running verifier;
- validates the local metadata root and bounded UTF-8 distribution name/PEP 440 version before trusting its identity;
- reads installed package/distribution metadata and package files only;
- ignores console-script entries outside package/distribution scope;
- never reads or mutates Instance originals, canonical knowledge, derived indexes, secrets or user configuration;
- caps RECORD processing, findings, cumulative hashing bytes and incremental package-entry traversal, including files and directories;
- rejects package-scoped traversal, symbolic-link escapes and filesystem reparse points.

Generated bytecode in standard `__pycache__` paths and common platform-generated regular files are excluded from unexpected-file detection because they are not authoritative wheel payload files. Top-level sourceless bytecode remains in scope because Python can import it directly.

## Official origin

Every local result includes a separate origin state:

`not_established`

The browser and API explain that official origin requires a trusted release manifest, signature or attestation. The current capability does not perform a hidden network lookup and does not equate package integrity with a verified official build.

Future work may allow an operator to supply a trusted local release bundle or signed manifest. That evidence should extend the origin result without weakening the local integrity checks.

## Interfaces

The shared application function is exposed through:

- `provelume verify-installation`;
- `GET /api/v1/security/installation`;
- `/security/installation` in the local Knowledge Browser.

All interfaces call the same verification logic and remain read-only.

## Consequences

Positive consequences:

- modified Core package files become visible without GitHub or network access;
- editable/development installs receive an honest unavailable state;
- the product language avoids false official-build claims;
- CLI, API and browser share one stable contract;
- the result can later feed `Settings -> Security` and privacy/trust status.

Limitations:

- package `RECORD` cannot authenticate its own publisher;
- console entrypoint scripts and interpreter/base-environment files are outside the first scope;
- installed runtime dependencies are not yet verified against the release SBOM/lock;
- container and future Windows installer inventories require platform-specific evidence.

## Follow-up

Add an optional trusted local release-manifest/signature anchor and compare installed package identity with the official release bundle. Later extend the same Security surface to runtime dependency inventory, plugin distinction and Privacy & Network Activity.
