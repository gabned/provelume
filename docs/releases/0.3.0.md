## Product outcome

An operator can optionally link the local installation verifier to an offline release bundle,
validate the released wheel and compare installed Core bytes with the released wheel bytes.
The existing RECORD-only path remains available and backward compatible.

## Evidence boundary

The release must distinguish three evidence layers:

1. local package bytes agree with installed distribution metadata;
2. installed bytes agree with a self-consistent release bundle and released wheel;
3. the same bundle matches an independently trusted manifest SHA-256 or a future accepted
   provider-independent signature.

Layers one and two do not authenticate official origin. User-facing and machine-readable
results must not use a generic green “official”, “safe” or equivalent absolute verdict.

## Implementation scope

- shared application-service support for an explicit local bundle input;
- bounded reuse of the shipped provider-independent bundle verifier;
- in-memory wheel identity, path, `RECORD` and package-byte validation;
- protection against unsafe names, links/reparse points, duplicates, malformed records,
  incomplete coverage and resource exhaustion;
- stable CLI and JSON output plus consistent read-only API and EN/IT browser presentation;
- regression coverage for a modified local RECORD that attempts to conceal changed installed
  bytes;
- documentation of exact positive, modified and unavailable outcomes.

## Excluded scope

- new detached-signature or key-management formats;
- online GitHub attestation lookup;
- runtime traffic observation or operating-system egress enforcement;
- issue #24 OCI builder work;
- issue #5 OCR/ingestion work;
- runtime dependency, plugin, container or Windows installer verification;
- Cloud, external AI, SaaS, billing or `provelume.com` changes;
- version bump, tag or publication in the implementation PR.

## Delivery sequence

1. one homogeneous product owner PR implements the #20 remainder without changing version;
2. exact-head Linux, Windows, clean-room, trusted-base and release dry-run gates pass;
3. the owner PR is merged and reconciled on `main`;
4. a separate release-preparation PR aligns package, embedded identity, changelog and public
   release documentation at `0.3.0`;
5. only the reviewed release-preparation result on current `main` may receive tag `v0.3.0`;
6. the permanent official release workflow rebuilds, verifies, attests and publishes the
   bundle after separate authorization.

## Exit gates

- valid, modified, missing, unsafe and malformed bundle/wheel/install cases fail or pass as
  specified by one stable result contract;
- cumulative file, metadata, member and hashing limits are deterministic and tested;
- no untrusted archive member is extracted onto the filesystem;
- no network request or Instance-data access occurs;
- RECORD-only behavior remains backward compatible;
- every interface uses claims no stronger than the evidence layer established;
- package identity remains `0.2.0` until the release-preparation step.
