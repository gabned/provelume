# ADR 0006: verify installed Core bytes in two trust modes

- Status: Accepted
- Date: 2026-08-23
- Deciders: Provelume maintainers

## Context

Offline release-bundle verification checks downloaded release material, but it
does not answer whether the files currently imported and executed by a local
Provelume installation have changed.

Python installations expose a `.dist-info/RECORD` inventory containing paths,
sizes and hashes. This is useful for detecting accidental corruption and local
modification. However, both package files and RECORD are local mutable state, so
RECORD alone is not an independent trust anchor.

A stronger comparison is possible when the operator also supplies a release
bundle that passes ADR 0005 verification. The released wheel contains its own
RECORD and the original Core package bytes. Comparing installed files with that
wheel prevents a locally rewritten RECORD from hiding divergence from the
release artifact.

The release manifest still lacks a detached provider-independent signature, so
neither mode should be labelled an authenticated official installation yet.

## Decision

Provelume Core will expose installation verification with the same three outcome
states used for release bundles:

- `verified` — the requested comparison completed and all checked identities
  match;
- `modified` — expected material exists but its path, inventory, size or digest
  differs;
- `unavailable` — required identity metadata is missing or unreadable.

Two trust modes are supported.

### Local RECORD mode

The verifier locates or accepts an explicit installed distribution RECORD and:

1. requires a single in-scope `.dist-info/METADATA`;
2. verifies package name and version;
3. checks every in-scope hashed file by recorded size and SHA-256;
4. ignores generated bytecode and reports generated script entries outside the
   site-packages root without following them;
5. rejects path aliases, Windows drive prefixes, escaping symlinks and symlinked
   Core files;
6. scans the installed `provelume/` tree for unrecorded files or symlinks.

A successful result is explicitly described as consistency with local RECORD,
not proof of official provenance.

### Release-wheel linkage mode

When a release bundle is provided, the verifier first requires that bundle to
pass the offline release checks. It then:

1. selects the single wheel matching the installed version;
2. validates wheel member paths, limits, symlink state and compression bounds;
3. validates the wheel's internal RECORD against member bytes;
4. compares the complete installed Core file inventory and SHA-256 identities
   with the released wheel.

The installed result is `verified` only if both local RECORD and release-wheel
comparisons succeed.

## Assurance statement

A local RECORD match means:

> Installed Provelume Core files are consistent with the mutable installation
> metadata currently present on this machine.

A release-wheel match additionally means:

> Installed Provelume Core files are byte-identical to the Core package files in
> the supplied, internally consistent release bundle.

Neither statement yet authenticates the release manifest signer or hosted
attestation offline.

## Consequences

- unexplained local file changes and unrecorded Core files become visible;
- editable installations without packaged Core identities cannot receive a
  false verified status;
- a modified RECORD cannot conceal divergence when release-wheel linkage is
  requested;
- generated scripts outside site-packages are never followed by the verifier;
- no network, GitHub, cloud or AI dependency is introduced;
- future UI can reuse structured findings and trust-mode status.

## Follow-up

After detached manifest signing exists, the release-wheel linkage result can be
promoted to a cryptographically authenticated official-build check. A later
runtime inventory should distinguish Core files, verified plugins, local
configuration and intentionally modified development installations.
