# Verify installed Provelume Core files

Provelume can inspect an installed Python distribution without contacting
GitHub, Provelume Cloud or any external AI provider.

This is the first application-layer capability behind the planned
**Settings → Security → Verify installation** experience.

## Run against the current environment

From a Provelume source checkout or environment where Provelume is installed:

```bash
python scripts/verify_installation.py
```

For stable machine-readable output:

```bash
python scripts/verify_installation.py --json
```

The JSON result follows `installation-verification-result.schema.json`.
Exit codes are:

| Exit code | Status | Meaning |
| --- | --- | --- |
| `0` | `verified` | Every requested installed-file comparison succeeded |
| `1` | `modified` | Expected material exists but a path, inventory or byte identity differs |
| `2` | `unavailable` | Required installation or verification metadata is unavailable |

## Local RECORD mode

Without another argument, the verifier locates the installed `provelume`
distribution and its `.dist-info/RECORD` file. It checks:

- package name and version from `METADATA`;
- recorded size and SHA-256 for every in-scope installed file;
- safe relative paths and installation-root containment;
- missing files, unexpected file types and symlinked Core files;
- unrecorded files or symlinks under the installed `provelume/` package;
- generated bytecode separately from durable Core files;
- generated console-script RECORD entries without following paths outside
  site-packages.

A local RECORD match is useful evidence of installation consistency, but RECORD
is mutable local state. It is not an independent proof that the installation
came from an official release.

Editable development installs that do not contain packaged Core identities do
not receive a false verified result.

## Link to a release wheel

For stronger byte linkage, provide a release bundle that already contains
`release-manifest.json`, `SHA256SUMS`, the wheel and SBOM:

```bash
python scripts/verify_installation.py \
  --release-bundle /path/to/provelume-release \
  --json
```

The verifier first runs the offline release-bundle checks. It then validates the
wheel as a bounded ZIP archive, verifies the wheel's internal RECORD and compares
the complete installed Core file inventory with the package files in that
wheel.

This catches a case where both an installed file and the local RECORD were
rewritten together: local RECORD mode alone can still match, while release-wheel
mode reports the divergence.

## Advanced explicit paths

Synthetic deployments or diagnostic tooling can supply an explicit
site-packages root and RECORD path:

```bash
python scripts/verify_installation.py \
  --root /path/to/site-packages \
  --record /path/to/site-packages/provelume-0.1.0.dist-info/RECORD
```

`--root` and `--record` must be provided together.

## Safety behavior

The verifier does not execute installed package code. It reads metadata and
files directly with bounded inventories and streaming SHA-256 calculations.
It rejects:

- absolute, drive-prefixed or malformed RECORD paths;
- traversal aliases that resolve back inside the installation;
- symlinked Core directories or files;
- wheel traversal, duplicate members, symlinks and suspicious compression;
- incomplete or unhashed durable Core identities;
- unexpected files under the installed Core package.

Paths for generated scripts outside site-packages are counted and reported, not
followed.

## Current trust boundary

A successful release-wheel comparison proves byte equality with the wheel in the
supplied internally consistent bundle. The release manifest is not yet protected
by a detached provider-independent signature, so this is not yet labelled
**Verified official build**.

The next trust milestone is offline manifest signature verification. Once that
exists, installation verification can combine authenticated release identity,
Core byte comparison, code-signing state and plugin/configuration boundaries in
one user-facing result.
